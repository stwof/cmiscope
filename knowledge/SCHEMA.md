# Knowledge Graph Data Schema

Source of truth: `data/knowledge_graph.json` (UTF-8, LF), generated by
`tools/build_kg.py`. On startup `cmis_service/db.py` reloads it into SQLite, so
the graph is queryable through `/api/kg/*` without any external graph database.

## Top-level object

| Key | Type | Description |
| --- | --- | --- |
| `meta` | object | Generator, version, counts, entity/relation type histograms, confidence and relation legends |
| `sources` | array | 38 provenance records |
| `entities` | array | 129 typed nodes |
| `relations` | array | 257 typed directed edges |
| `links` | array | 268 joins between the graph and CMIS fields / devices |
| `pending_confirmations` | array | 19 open verification items |

## `sources[]`

| Field | Type | Notes |
| --- | --- | --- |
| `source_id` | string | Primary key, referenced by `source_ids` everywhere else |
| `title`, `publisher`, `kind`, `license`, `note` | string | Descriptive metadata |
| `url` | string | Canonical link (all 38 entries have one) |
| `retrieved_at` | string | ISO date of the last verification |
| `confidence` | string | `confirmed` / `partial` / `pending` |

## `entities[]`

| Field | Type | Notes |
| --- | --- | --- |
| `entity_id` | string | Primary key, e.g. `SEC-VDM`, `IF-CDB-FRAME`, `CFG-APPSEL` |
| `type` | string | One of 12 types (below) |
| `name`, `summary` | string | Display text (Chinese in the shipped data; English names are provided where available) |
| `source_ids` | array of string | Must all resolve to `sources[].source_id` |
| `confidence` | string | `confirmed` / `partial` / `pending` |
| `status` | string | `active` or `needs_review` |
| `attrs` | object | Type-specific extra attributes |

Entity types: `Organization`, `Standard`, `SpecClause`, `Interface`, `Module`,
`Device`, `ConfigItem`, `Concept`, `OpenSourceProject`, `Service`,
`SpecificationPartition`, `AccessPath`.

`SpecificationPartition` holds the four CMIS partitions exposed by the
dashboard: `SEC-LOW-PAGE`, `SEC-VDM`, `SEC-CDB`, `SEC-CONTROL`.
`AccessPath` holds the three transport options: `IF-MIRROR`, `IF-SSH-I2C`,
`IF-REST-API`.

## `relations[]`

| Field | Type | Notes |
| --- | --- | --- |
| `relation_id` | string | Primary key |
| `src`, `dst` | string | Both must resolve to `entities[].entity_id` |
| `type` | string | One of 11 types (below) |
| `label`, `source_ids`, `confidence`, `status`, `attrs` | mixed | Same conventions as entities |

Relation types: `DEFINES`, `CONTAINS`, `CONFIGURES`, `REFERENCES`,
`IMPLEMENTS`, `CONSTRAINS`, `MONITORS`, `ADVERTISES`, `DERIVES_FROM`,
`INTEGRATES`, `INSTANTIATES`. These cover the required containment,
definition, constraint, implementation and reference semantics.

## `links[]`

| Field | Type | Notes |
| --- | --- | --- |
| `cmis_ref` | string | A CMIS `field_key` (e.g. `CdbCmdId`) or a `device_id` |
| `entity_id` | string | Graph entity this reference resolves to |
| `relation` | string | Join role, e.g. `config_item`, `belongs_to_section` |
| `note` | string | Optional explanation |

Links enable bidirectional queries:

```
GET /api/kg/link?cmis=AppSelLane1     # field -> graph
GET /api/kg/link?cmis=CdbCmdId        # CDB field -> CFG-CDB / SEC-CDB / spec / implementation
GET /api/kg/link?entity=CFG-APPSEL    # graph entity -> fields and devices
```

## `pending_confirmations[]`

| Field | Type | Notes |
| --- | --- | --- |
| `pending_id` | string | `P-01` ... `P-19` |
| `topic`, `question`, `impact` | string | What is unverified and why it matters |
| `source_ids` | array of string | Sources to check against |
| `status` | string | Currently `open` for all items |

## SQLite mapping

| JSON array | Table | Loaded on startup |
| --- | --- | --- |
| `sources` | `kg_sources` | cleared and reinserted |
| `entities` | `kg_entities` | cleared and reinserted |
| `relations` | `kg_relations` | cleared and reinserted |
| `links` | `kg_links` | cleared and reinserted |
| `pending_confirmations` | `kg_pending` | cleared and reinserted |

Because the graph is rebuilt on every start, editing the JSON (or its
generator) and restarting the service is sufficient; no database migration is
needed for graph changes. Device/config-item data is synchronized separately
with `INSERT OR IGNORE`, so operator edits survive restarts.

## Integrity checks performed by the generator

- Every relation endpoint resolves to an existing entity.
- Every `source_ids` entry resolves to a defined source.
- Every `links[].entity_id` resolves to an existing entity.
- Entity and relation type histograms are emitted into `meta` for verification.
